## Overview

I built this simulation to practise feeder monitoring, supervisory control and fault diagnosis in Ignition Perspective. It combines an operator-facing view with simulated electrical measurements and deterministic control behaviour.

My work covered the Tag structure, Perspective bindings and event scripts, control interlocks, command-feedback checking, and alarm activation, acknowledgement and recovery.

## Architecture & approach [#architecture]

The application runs within Ignition using a writable default Tag Provider. Commands, Measurements, Status and Simulation are separate Tag groups, keeping operator requests distinct from equipment feedback and fault injection.

Perspective presents measurements and status, while event scripts and expression bindings connect the controls to the simulation. The exported close-permissive expression checks remote mode, healthy communications, absence of a protection trip and load below its configured threshold.

### Tag organisation

```text
[default]Feeder01
├── Commands      Open / close / trip-reset requests
├── Measurements  Voltage / current / load / frequency
├── Status        Feedback / permissives / alarms
└── Simulation    Fault switches / targets / timers
```

## Command-feedback validation [#command-validation]

A button request, an accepted command and breaker feedback represent different stages of an operation. Commands rejected by an interlock do not start the feedback timer because they have not been sent to the simulated device.

After a valid command is accepted, the logic waits for the expected breaker feedback. The project documentation describes a timeout of approximately two seconds; missing feedback raises a command-failure alarm.

## Protection & recovery [#protection-recovery]

A sustained simulated overload produces a high-load alarm and a delayed protection trip. The trip opens the breaker and prevents another close command until the overload is removed and the trip is reset.

Alarm acknowledgement and recovery are separate actions. Acknowledging an alarm records operator attention; removing the fault and restoring the appropriate state allows it to clear. A successful command retry clears the command-failure condition.

## Outcomes & lessons [#outcomes]

The implemented simulation brings telemetry, breaker supervision, interlocks, feedback checking and alarm handling into one operator view. It provided practical experience separating command intent from observed state and diagnosing fault conditions through Tags and alarms.

The model remains a learning environment with simulated equipment. Planned extensions include PLC connectivity through OPC UA, historical trending and operator action records; these are not implemented capabilities of this case study.
