# 视觉与交互规范

本文件规定网站的长期视觉方向。职业定位与内容真实性以 [business.md](business.md) 为准，代码组织以 [coding-style.md](coding-style.md) 为准。具体颜色、尺寸及复用样式以 `src/styles/global.css` 为唯一实现来源；本文说明如何使用，不复制一套设计值。以下是后续视觉改动的判断依据，不表示相应版式已全部实现。

## 视觉 brief

- **受众与任务：**招聘人员快速判断职业方向、查看可信的项目证据并找到联系方式；技术评估者可继续阅读实现与验证细节。具体访问路径以 business.md 为准。
- **目标感受：**冷静、可靠、清晰，带有工程工作的严谨感。辨识度来自真实案例的组织、排版节奏与克制的技术标注，不靠模拟生产监控画面。
- **视觉隐喻：**一份可浏览的工程案例记录。先呈现结论和个人贡献，再展开方法与证据；细线、年份和等宽元数据承担定位作用，不能替代正文。
- **构图与层级：**首页给职业方向和主要入口足够空间；项目是内容重心；About 用连续叙事建立背景；Blog 保持文章的阅读节奏。大标题、窄阅读列与局部深色表面形成对比，避免每节都套同一种卡片。
- **色彩与字体：**沿用现有深色蓝灰 token。大段内容用 sans，少量可信的技术元数据用 mono；单屏只有一个主要视觉动作。
- **交互与边界：**导航、筛选、展开、简历和联系入口要在键盘与窄屏上可用；无需 JavaScript 仍能读到核心内容。没有事实来源的指标、流程图、监控状态和媒体不进入设计。

## 设计原则

**Engineering Portfolio, not SCADA Dashboard.** 以专业、简洁、理性的工程作品集为主体。招聘人员应先看到职业方向、个人贡献、实现方法和验证证据，再看到装饰。允许少量工业控制台语汇帮助阅读技术内容，不将整站做成操作界面。

- 信息顺序：首屏说明身份、方向、代表能力及联系入口 → 精选项目与工程证据 → 经历与教育 → 集中联系区；Blog 为补充。
- 大标题、适度留白、清楚的正文层级与细边框建立秩序。背景和装饰不承担关键信息。
- 项目卡片优先呈现仿真环境、个人实现、测试或联调证据和真实源码/Demo 链接。没有提供的架构图、指标、运行状态或演示不补造。
- 工业语汇限于等宽的年份、技术参数、工具名、标签与确有依据的架构示意。状态色只对应真实状态，不以绿色暗示项目已投产。

## 页面构图与信息节奏

| 页面 | 主视觉任务 | 推荐的组织方式 |
| --- | --- | --- |
| Home | 让访问者迅速识别职业方向并进入作品 | Hero 的姓名与方向先于标签和按钮；精选项目紧接首屏，展示两项仿真案例的不同工程侧重点；背景与联系区作为后续阅读节点。Hero 粒子只能衬托文字。 |
| Projects | 让访问者判断做了什么、如何做、如何验证 | 列表使用真实封面、摘要与少量技术标签，整张卡片进入详情。详情先展示成果媒体，再以技术章节解释方法，证据紧邻对应论述；正文不以折叠隐藏。 |
| About | 解释经历如何支撑当前方向 | 引言、能力、经历和教育形成连续阅读路径。桌面页内导航帮助定位，窄屏回到正常文流；时间与组织是索引，具体贡献是阅读主体。 |
| Blog | 让读者持续阅读技术思考 | 列表突出题目、日期和摘要；正文使用窄阅读列，代码和表格按需横向滚动。空列表诚实说明状态，不以示例文章填充。 |

同一页面用留白、标题和细分隔线区分章节；卡片留给能独立浏览的项目、经历、文章或联系模块。首页的开阔 Hero、About 的导航与叙事、Blog 的窄阅读列可以有不同构图，但共享字体层级、边框和动作规则。项目卡片因真实内容长短而调整排布，不为了视觉对称补写文字或制造同等数量的标签。新增视觉元素前先确认它帮助访客定位、理解贡献或采取下一步动作。

## 主题与色彩

当前仅有深色主题。`global.css` 的 `--bg`、`--surface`、`--card` 负责背景层级；`--text`、`--text-secondary`、`--text-muted` 负责文字层级；`--accent` 表示链接和关键提示；`--primary` 表示主要动作。低饱和蓝灰是主色，不新增霓虹渐变作为页面或卡片的常规外观。通过字重、留白和表面层级建立重点，不能只靠亮色凸显内容。

- 文字与底色选择以可读性为先：普通文字目标 WCAG AA 对比度至少 4.5:1；可辨识的交互边界和焦点状态至少 3:1。不能单靠颜色说明筛选、状态或链接含义。
- `--border` 与 `--border-light` 用于卡片分隔；按钮和表单边界使用对比更强的 `--border-control`。焦点使用全局 `:focus-visible` 的轮廓，不以 hover 代替。
- `--success`、`--warning`、`--danger` 只用于经事实确认且需要语义区分的状态。项目生命周期未知时省略状态标签。
- 新增或修改颜色时检查实际前景/背景组合，更新 `pnpm run verify:design` 的代表性配对；脚本覆盖常用 token 配对，仍需用浏览器审查真实页面与其他组合。

## 排版与布局

- 正文用系统 sans，技术元数据和短标签用 `--font-mono`。长段经历、项目描述和文章正文保持 sans，不用全页等宽字体。
- 每页一个 h1，章节用 h2，卡片标题用 h3 或按真实层级选择；字号由 `--size-*` 控制。`eyebrow` 是辅助标注，不能替代标题。
- 使用 `.container` 作为宽版页面边界、`.container--text` 作为文章和窄阅读内容边界；组件内部通过 `--space-*`、`--section-gap`、`--page-gutter` 建立间距。窄屏改为单列并保留自然换行。
- 长技术名、链接和代码片段允许换行或局部横向滚动，不裁掉关键内容。固定导航下的主标题与页内锚点应有可见空间。
- 主导航每个入口使用等宽单元，图标、标签和激活状态保持相同的对齐区域；在 320px 宽度也不能截断标签。
- 长列表先给可扫描的标题、摘要和少量关键要点，详细内容再交给原生展开交互；不同密度的内容不必强行填满同高卡片。

## 组件用法

| 需求 | 现有用法 | 生成约束 |
| --- | --- | --- |
| 主要与次要动作 | `.action-link`、`.action-link--primary` | 一屏只强调最有用的主要动作；href 必须真实有效 |
| 项目、经历与文章卡片 | `.surface-card`、`--card-padding` | 独立内容需要表面时使用；统一边框、圆角与内边距，结构按领域组件维护 |
| 技术栈、领域和年份 | `.tag-list`、`.tag`、`.technical-meta` | 标签是阅读辅助，不用密集假仪表或“熟练度”条 |
| 小节标注与标题 | `.eyebrow`、`.section-heading` | 用真实标题层级表达页面结构 |
| 正文与空状态 | `.prose`、`.empty-state` | 文章长文与无内容状态保持可读，不用占位事实 |
| 页面引言 | `.page-intro` | Projects 与 Blog 等内容页复用次要正文色和阅读宽度 |
| 长经历 | 原生 `<details>`、`.detail-disclosure` | 默认展示身份、简介和首要贡献；展开后连续显示完整 bullet list，提示切换为 `Show less`，无 JavaScript 时仍可操作。项目改用独立详情页 |

共享 recipe 放在 `global.css`，领域布局和局部状态放在 Astro scoped CSS。新组件先复用现有 token 与 recipe；确实多处使用时再增加共享规则。旧版未被页面使用的 ExperienceHero、ExperienceFeatured、ExperienceStats、ExperienceTechSummary 源文件含历史视觉写法，不作为新页面样式模板；重新启用前应先核对事实和本规范。

## 媒体与图示

只有在真实截图、架构图或演示能让读者更快理解系统行为时才加入媒体。图示须与项目已提供的设备、信号、软件和仿真范围一致，并清楚标识个人仿真；技术截图使用 contain，默认 16:9，允许 native 原始比例，不裁掉关键 UI 或拉伸。外部媒体缺失时保持文字案例完整，不添加空框、假波形、占位设备照片或不能打开的 Demo 按钮。装饰性背景不能覆盖文字、抢走主动作，也不能承担唯一的信息通道。

ProjectCard 与 ProjectDetailLayout 共享既有 token：卡片封面统一 16:9，边框 hover 不位移；详情为成果 Hero、页内索引和编号技术章节。ProjectGallery 支持 featured、comparison 与 sequence，双列在窄屏改成单列。每项重要证据采用 `Figure 01 — Title` 与 1–2 句工程说明，alt 只描述可见内容；Figure 根据实际阅读顺序自动编号。原图链接可通过浏览器放大，视频使用 Poster 和原生 controls，默认不自动播放。完整字段与来源要求见 [项目展示维护规范](project-showcase.md)。

## 动效与访问方式

首页粒子以昨天之前的最后一次提交 `e9ea692`（2026-06-06）为回溯基准，使用 `particles.js`：`Home.astro` 中的 `#particles-js` 容器和原版加载脚本、`src/assets/particles.json` 原配置、`src/assets/js/particles.min.js` 供应商脚本。恢复 160 个白色粒子、移动速度 1、透明度动画及原版径向渐变背景，容器不再额外降低透明度。粒子仅在 Hero 内，低于正文且不接收指针事件。原版只在页面加载时检查 `prefers-reduced-motion`；开启减少动效时不加载供应商脚本、不创建 canvas，切换偏好后需重新加载页面才能应用。关闭 JavaScript 时不会生成粒子。文字和链接不依赖粒子显示。

交互要能通过键盘使用，焦点清楚可见；筛选按钮同时提供文字、`aria-pressed` 和可读的结果数量。移动端优先保证导航、项目证据和联系入口可达。图像有合适的 alt 与尺寸；纯装饰使用空 alt 或 `aria-hidden`。

## 视觉评审方式

改动页面视觉时先写一句本次要强化的判断，例如“读者应先看见仿真项目的个人贡献，再看技术标签”；选择一张代表性页面或状态实现，然后查看实际运行截图。桌面与窄屏分别检查：第一眼焦点是否明确、案例证据是否比装饰更突出、同类元素是否一致、是否出现重复说明或无用容器、主要动作及焦点是否可见。优先修正最影响阅读的 1–3 个问题，再复核截图。截图只能证明所见视口的视觉状态；功能、对比度与减少动效还需分别验证。没有截图时明确记录视觉复核未完成。

## 生成后的验收

1. 核对 Home、About、Projects、Blog 的标题层级、卡片、按钮、技术标注和空状态是否一致；同时检查四页是否各自完成其主视觉任务。
2. 在至少桌面和 390px/320px 视口检查导航遮挡、横向溢出、长文字换行和焦点可见性。
3. 对新颜色运行 `pnpm run verify:design`，对代码改动运行 `pnpm run build`；改变列表/导航时按 [workflows.md](workflows.md) 运行 `verify:site`。
4. 检查正常与减少动效偏好下的 Hero，以及禁用 JavaScript 时的关键信息。未实际执行的浏览器、WCAG 全站审计或性能检查不要写成已通过。
