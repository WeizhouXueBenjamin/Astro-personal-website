## Overview

This local simulation links CODESYS Control Win to a Factory I/O conveyor scene. I worked on the signal mapping and Structured Text sequence logic coordinating sensors, conveyors, a turntable and transfer operations.

The scene and initial PLC sample came from the Factory I/O CODESYS OPC UA tutorial. My documented changes separate the simulation addresses from the control logic and replace multiple sequence-state Boolean variables with one explicit state machine.

## Architecture & I/O boundary [#architecture]

CODESYS Control Win acts as the SoftPLC and exchanges signals with Factory I/O over OPC UA. Factory I/O addresses are confined to the input and output mapping boundary, keeping the sequence logic independent of those addresses.

Input mappings translate FIO.i variables into internal feedback variables. The logic produces internal actuator commands, which are mapped back to FIO.o outputs.

### Documented control path

```text
Factory I/O sensors
  → PLC input mapping
  → Internal feedback
  → Sequence / machine logic
  → Actuator commands
  → PLC output mapping
  → Factory I/O actuators
```

- [Read the architecture notes](https://github.com/WeizhouXueBenjamin/smart-conveyor-sorting-codesys/blob/main/notes/PLC%20Architecture%20-%2015Aug2026.md)

## Sequence control [#sequence-control]

A single E_SequenceState variable represents the current turntable stage. The documented sequence progresses through loading, rotation to unload, discharge and return to the loading position before returning to idle.

Separating feedback from actuator commands makes each stage easier to inspect. My project work also included diagnosing retained-state and timing faults and verifying the corrected end-to-end operating cycle.

### Turntable state sequence

```text
SEQ_IDLE
  → SEQ_LOADING
  → SEQ_ROTATE_TO_UNLOAD
  → SEQ_DISCHARGING
  → SEQ_RETURN_TO_LOAD
  → SEQ_IDLE
```

> A single sequence-state variable makes the active stage explicit, instead of requiring several independent Boolean state flags to remain consistent.

## Connection & mapping diagnosis [#integration]

The first integration problem was a mismatch between the runtime security settings and the sample's anonymous OPC UA connection. After correcting the local simulation configuration, Factory I/O could browse all 18 FIO variables.

A subsequent null-reference error remained even though the variables were visible. I rebuilt the scene's saved I/O mappings against the current runtime; the error disappeared and the 18 signals could be exchanged without changing the PLC logic for these setup fixes.

Anonymous access was used only for this single-computer simulation. It is a limitation of the local setup, not a recommended access policy for a deployed control system.

> Successful variable browsing isolated the second fault to the mapping layer. A running PLC and a working connection still require separate checks of the machine sequence.

## Outcomes & next development [#outcomes]

The documented work establishes a working simulation connection, corrected I/O mapping, separate feedback and command layers, and a single state machine for the turntable sequence.

The key lesson was to diagnose runtime, endpoint, permissions, symbols, mappings and machine movement as separate checks. Restoring communications does not establish that the control sequence is correct.

Manual/Auto modes, operator requests, permissives and fault handling remain architecture placeholders in the project notes. Interlock validation, blockage or jam detection, fault recovery and FAT/SAT-style documentation are planned work, not demonstrated outcomes.
