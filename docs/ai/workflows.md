# AI 任务流程与验收

项目入口为 [../../AGENTS.md](../../AGENTS.md)。先按业务领域与变更种类选择需要读取的资料，不要求每次通读全部文档。

## 任务输入

自然语言需求足够清楚时直接工作，不要求所有者补齐固定表单。复杂任务可以用以下结构减少遗漏：

```yaml
goal: 本次希望改善的用户行为或结果
scope: 允许修改的页面、组件、内容或配置
facts: 已提供的真实内容、文件及业务依据
constraints: 需要保留的行为、样式和兼容要求
acceptance: 可以观察和验证的完成条件
```

重要输入是用户目标与验收，而非强制要求所有者先指定实现方式。

## 先决定，再生成

1. 读取相关文件、工作区差异和必要的 instructions，识别现有修改。
2. 对照 [business.md](business.md)，区分已确认目标、现有行为与待决定事项。
3. 缺少会改变定位、内容真实性、信息架构或实施范围的决定时，集中提出少量问题；其他可独立推进的部分继续进行。
4. 说明本次影响范围，复用已有布局、集合和组件完成最小完整改动。
5. 根据受影响行为验证，检查 diff，并同步确实发生变化的规则或模板。
6. 交付时说明结果、修改文件、实际验证及仍需所有者提供的内容；不把未执行检查写成已通过。

已经确认的决定不反复询问。常规命名、函数拆分和局部排版由 AI 结合现有模式处理。

## 按任务选择检查点

| 任务 | 先读 | 需要交付的完整链路 | 验证重点 |
| --- | --- | --- | --- |
| 新增/更新经历 | experience schema、现有条目、About/Experience 消费者 | 真实数据 → 统一数据源 → 涉及的概览/详情 | 必需字段、日期、排序、无占位推荐材料、build |
| 新增/更新项目 | projects schema、ProjectList 与列表项 | 真实条目 → 集合读取 → 卡片/过滤/可选链接 | 无内容与缺少可选链接、标签筛选、build |
| 发布 Blog | blogs schema、列表、详情、RSS | 文章 → 一致发布过滤 → 正确路径/metadata/RSS | draft、标题层级、RSS 条目、build |
| 新增或调整页面 | 对应业务职责、现有路由与布局、导航数据 | 路由 → 数据 → 布局 → 入口和导航状态 | 重复职责、移动端、键盘、metadata、build |
| 合并 About/Experience | 已确认业务方向、两页所有消费者 | 单一职业背景页 → 导航 → 旧地址处理 → 数据一致性 | 不丢真实经历/教育/技能，旧路径行为有证据 |
| 新增通用组件 | 同类组件、当前调用者、主题 token | 真实调用需求 → typed Props → 组件 → 页面接入 | 缺少可选值、不同内容长度、焦点/交互、build |
| 调整视觉风格 | [设计规范](design-system.md)、共享 token、受影响页面 | 确认方向 → token/recipe → 局部组件 → 浏览器核对 | 对比度、卡片与动作一致性、窄屏、减少动效、build 与 verify:design |
| schema 迁移 | schema、全部内容与消费者、文档模板 | 新契约 → 内容迁移 → 消费者 → 同步示例 | 不静默丢字段、不以空值伪造内容，build |
| 修复缺陷 | 对应代码和可复现症状 | 触发条件 → 原因 → 修复 → 行为验证 | 针对问题验证，区分原有与新增告警 |
| 只改文档 | 对应规则来源与当前代码 | 事实/目标分清 → 链接完整 → 不重复定义 | 相对链接、术语与命令准确，不运行无关测试 |

上表是受影响范围的导航，不是要求一次任务完成全项目改造。

## 可直接使用的任务示例

### 接入真实项目集合

> 按 AGENTS.md 和 docs/ai 中的约定，将 Projects 接入现有 projects 集合。复用标签过滤组件，处理集合为空以及没有可选链接的状态。只使用我提供的项目事实，不生成虚构条目。运行构建并验证实际列表与链接行为。

### 合并职业背景页

> 按已确认的信息架构合并 About 与 Experience，优先沿用 /about。保留已提供的职业经历、教育与技能，避免维护重复数据。同步导航，并给出 /experience 与 /gallery 旧地址的明确处理。遵循统一深色设计规范，验证构建和受影响路由。

### 增加经历

> 根据我提供的事实新增一条 experience。先检查运行时 schema，使用现有字段命名；没有推荐材料就省略，不构造占位内容。检查相关页面的排序和展示，并验证构建。

### 修复 Blog 发布链路

> 统一 Blog 列表、详情静态路径和 RSS 的 blogs 集合读取及 draft 过滤，确保草稿没有公开详情路径或 sitemap 条目。修复重复主标题，验证生成的文章页面与 RSS。保持现有文章 URL。

这些示例用于后续发起任务，每次按当次需求确定范围。当前已经确认自动化与系统集成定位，并授权了栏目合并、页面导航和相关内容链路的改造，不需要重新询问这些决定。

## 项目内容生成示例

> 按 projects 的运行时 schema 整理我提供的自动化项目事实。突出工程场景、PLC/SCADA 或软件层的个人实现、联锁与故障处理、联调和验证证据。明确是个人仿真还是实际现场交付。没有提供的设备、协议、指标、项目状态和生产部署不要补写。同步检查首页精选与 Projects 卡片的显示。

涉及集合、发布过滤、导航或跳转的任务运行 `pnpm run build` 与 `pnpm run verify:site`。页面布局或交互变更可补充本地浏览器检查相关视口与行为，选用当时可用且获授权的工具；不要求引入 Playwright。没有执行浏览器检查时，应如实报告验证边界。

调整颜色或文字/控件背景配对时运行 `pnpm run verify:design`，并目视检查页面实际状态。这个脚本只覆盖列出的 token 配对，不等于自动完成全站 WCAG 审核。

## 规则维护

- 所有者修改业务决定时，先更新 business，再修改受影响代码；不要复制到多个入口形成不同版本。
- 配置或 schema 变化时同步 engineering 中确实受影响的约定与模板。审计是带日期快照，不能用改写旧证据来假装已做过新验证。
- AGENTS 只保留高频约束和资料导航。重复的具体反馈放到最接近相应领域的文档中。
- 不把单次任务中的临时要求自动升级为永久规范；需要长期保留时说明适用范围。
